# 44. Durable token budgets for virtual keys
Status: Accepted (2026-10-28). Extends [0008](0008-virtual-keys.md), [0012](0012-unknown-usage-never-zero.md), [0016](0016-fail-closed-when-log-unavailable.md). Extends request transformation in [0009](0009-inspect-whole-request.md) for budgeted keys.
## Context
Virtual keys restrict providers and models but cannot bound an employee's token use. Post-response totals alone allow concurrent requests to spend the same balance. Usage can be absent after errors or interrupted streams, and a proxy can restart while requests are in flight.
## Decision
- Optional `keys[].tokenBudget` declares UTC calendar `day` or `month`, separate `inputTokens` and `outputTokens`, and positive `maxOutputTokens` per request. Limits share the virtual key hash across providers, names and processes using the same budget directory. Duplicate hashes involving a budgeted key are refused at startup.
- Before generation, the proxy inspects the request, sets or clamps its output cap, counts its sanitized input with the provider, and reserves input plus the output cap atomically. Responses uses `/v1/responses/input_tokens`; Messages uses `/v1/messages/count_tokens`. Counting failures refuse generation. Chat Completions is refused for budgeted keys; unbudgeted keys keep its existing behavior.
- Stateful Responses references, background generation and provider-executed tools are refused for budgeted keys: a preflight cannot bound input added by subsequent provider activity. Client-executed function tools remain supported. A count is a provider preflight, not locally measured generation usage; Anthropic documents counts as estimates.
- Reservations live in separate versioned owner-only JSON files under `budgetDirectory`, default `<log>.budgets`. An exclusive file lock protects read/check/write across processes. Atomic replacement and file/directory fsync preserve state. Lock contention, corrupt state and I/O failures fail closed. Locks are never automatically stolen.
- Complete reported usage replaces the reservation per field. Anthropic cached and cache-write input is included. Missing usage retains that field's full reservation. Network errors retain both; reservations left by crashes never expire within their period. No unknown usage is fabricated in the audit log.
- Reported usage above a reservation is charged in full and blocks the key for the rest of that period. Provider undercounting or violation of output caps can therefore exceed an allowance on that request; this is an admission budget, not a provider billing guarantee.
- Exhausted budgets return 429, unsupported budgeted requests 422, unavailable accounting/counting 503. A refusal writes one ordinary request record and makes no generation call. Settlement failures retain pending liability and increment a metric without suppressing the request audit record.
- `GET /audit/budgets` requires the admin credential and reports current limits, spent, reserved, remaining and blocked state by key name. A request remains assigned to its admission period even when it finishes after rollover.
## Consequences
- Deployments must preserve the budget directory and share it on a local filesystem across their proxy processes. Deleting it, changing key hashes or periods, or using separate directories establishes a new allowance; operators control these actions. This is not a distributed database.
- Budgeted calls add a provider preflight and persistent writes. Budgeted clients must use supported request shapes. No real keys, prompts or responses enter the accounting files.
- Crash recovery can strand budget conservatively. An operator must stop writers before investigating an abandoned lock or state; automatic refunds would permit overspending.
