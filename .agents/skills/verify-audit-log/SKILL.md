# Verify the audit log and request lifecycle

## What is verified
| Property (TLA+ name) | Plain sentence | Harm if broken |
|---|---|---|
| ChainIntact (`spec/AuditChain.tla`) | With several writer processes, rotation, one crash, one prune and one clock step back at any step, `checkSeries` accepts the files in `files()` order: each file chains from genesis, each file after the first starts with a `segment` record that links to the file before it, and a missing first predecessor is listed by a `prune` record. | `ai-audit verify` reports a broken series; the log stops being evidence. |
| NoLostEntries | Every appended record is in a present file or in a segment that prune deleted. | Records vanish without a prune record. |
| AnchorsConsistent | `verifyAnchors` accepts every anchor: it matches a record at its position in some file, or the file it names by `first` is gone and a `prune` record lists it (ADR 0056). | Anchors falsely flag (or miss) a swapped log. |
| AtMostOneLog, NeverZeroWhenUnseen (`spec/RequestLifecycle.tla`) | A request writes at most one record, `llm-call` or `refusal`, and usage is recorded only when the provider sent it (ADR 0009, 0012, 0047). | Double counting, or totals that look complete but are not. |
| NoForwardOnBadLog | A request is never forwarded while the log is already unwritable or torn. | Calls go upstream with no audit record. |
| NoCrash, NeverSilent | A failed append never crashes the process; every request ends with a record or a counted failure, also when an error that is not a log failure is thrown before or after forwarding (e941677, fc88731). | Proxy dies (all clients drop); records lost without trace. |
| NoRefusalAfterForward | An error after the provider answered is counted as a lost record, never written as a refusal. | The log says "refused 500" for a call the provider answered. |
| NoForwardWithoutLog (residual cfg, expected to FAIL) | Strict: anything delivered is also logged. Not guaranteed: the log can break, or the disk can fill, after the last check (ADR 0016). | Known, counted by `metrics.logWriteFailures`. |
| WaitingAppNeverFlagged (`spec/DecisionLoop.tla`) | An application that waits for the verdict is never flagged as acting without approval, because a decision takes one verdict (ADR 0057). | The console reports "ran without approval" for an app that did what it was told. |
| NoActAgainstEarlierVerdict | No application acts when a person recorded `rejected` or `overridden` before it decided, because it checks before an action the rule allows. | An action runs after a person took the case over. |
| NeverFlagged (residual cfg, expected to FAIL) | Strict: no application that follows the protocol is ever flagged. Not guaranteed: a verdict can land between the check and the effect record of a rule-allowed action (ADR 0057). | Known; the console flags it for a person to look at. |
| ApprovalIsActedOn (unacted cfg, expected to FAIL) | Strict: once the application finished, an approved decision has its action done. Not guaranteed: an approval can come after the wait timed out (ADR 0057). | Known; the console lists it under Needs attention after `--overdue-minutes`. |

Bounds: AuditChain 2 writer processes x 2 appends, rotation when the current file holds 2 records, one crash of a writer or of prune, one prune of any oldest run of closed segments, 2 anchors, one step back of the clock to any earlier millisecond (1,109,143 distinct states, about 5 s). At f6b1865 the model of the code before ADR 0056, without the clock step, also passed with 3 writer processes (28,157,528 distinct states, 471 s, run by hand, not in CI); the current model was not run with 3. RequestLifecycle: one request with client close, timeout, usage chunk, the log going bad, the disk filling, and one internal error at any step (148 distinct states). DecisionLoop: one decision, a verdict at any time, an application that follows the protocol (52 distinct states). The laws in `test/laws.test.ts` add 90 generated requests through the proxy (three APIs, all modes, some with Quinelings tool calls and results) and 300 tampered logs.

Assumptions:
- Within one process, `writeFileSync` of `<log>.segment` and the `renameSync` into place are two steps, but no reader sees the first: the current file appears with its record. `AuditChain_emptysegment.cfg` models the old open-then-write start.
- The budget `count_tokens` call (ADR 0044) is not a forward. ADR 0009 scans `count_tokens` and does not log it, so it can reach the provider between the two `ensureWritable()` checks.

Not covered: the stale-lock takeover race (>10 s stall of a live holder; a dead holder is the `Crash` action), network filesystems, power loss without fsync, a lock-free `verify` that reads a partly written last line, the refusal rate limit (suppressed refusals are counted in one later record), attachments, routing, stats math, the order of a QDL decision's `program`, decision and `:qdl` records relative to other writers (each append is atomic; the group is not, which ADR 0026 accepts), a prune between the read and the append in `approve` or `effect` (it can leave a record whose decision is gone), an application that crashes after it acted and before it recorded the effect, and an application that does not follow the protocol.

Findings 1 to 8 are fixed; 7 and 8 by ADR 0057, which keeps two known windows of the decision loop. Traces and replays: `docs/verification/README.md`. Chart of the decision loop: `docs/verification/decision-loop.mmd`, labels from `docs/verification/decision-loop.view.mjs` for `/statechart`.

## Reading a failure
- `FAIL spec/...cfg: expected pass, got fail`: TLC prints a trace. Map each AuditChain step to the code: `Acquire` = `withLock` takes the lock file; `Rotate` = the `rotateBytes` check, `segmentTime` (`RotationName`) and `renameSync` in `rotateLocked` (a name that exists is `Fail`); `Check` = the missing-or-empty test before `startSegment` in `append`; `StartSegment` = `startSegment` reads the newest closed segment, writes `<log>.segment` and renames it into place (in the emptysegment config, `StartSegment` and `Fill` are the old open, then write); `ReadTail` = `lastHash()`; `Write` = `appendFileSync` and unlock; `Crash` = the process dies inside `withLock`, and the next writer takes the stale lock; `PruneRead` = `prune` lists the old segments without the lock; `PruneRecord` = its `log.append`; `PruneUnlink` = one `unlinkSync`; `AnchorRead`/`AnchorWrite` = `anchor()` reads the current file, then appends to the anchors file; `ClockStepBack` = the wall clock moves back. RequestLifecycle: `Start` and `Forward` = the two `ensureWritable()` checks; `BlockOrReject` = `reject()`, the block `write` or the budget-reject `write`; `FetchErr` = the fetch catch; `Headers` = `forwarded = true`; `Final` = the `write(...)` after the response; `InternalError` = any other throw; `Catch` = the outer `catch`; `LogGoesBad` = torn line or unwritable file; `DiskFills` = `appendFileSync` throws `ENOSPC`, which `ensureWritable()` cannot see. DecisionLoop: `PersonReviews` = `approve` or the console's verdict (refused when the decision has one); `RuleAllows` = the app finds the action `simulated` in `proposedActions`, checks with `await --timeout-s 0` and acts unless a person said no; `AppAwaits` and `VerdictArrives` = `awaitVerdict` returns the latest review; `AwaitTimesOut` = it returns `timeout`, and the app records `skipped` with code `timeout`; `AppActs` = the application's own action; `AppRecordsDone`/`AppRecordsSkip` = `log.effect`; `Authorized` = `effectAuthorized`. If the trace can happen in the code, it is a bug: write a failing test in `test/logsafety.test.ts` or `test/segments.test.ts` before fixing.
- `expected fail, got pass` on a mutant cfg: the model lost its teeth (an action changed so the bad variant no longer differs). Fix the model, not the cfg.
- `expected finding, got pass`: a config marked `finding` in `spec/run.sh` is an open bug, and a fix for it landed. Replay the old trace against the code, then change the line in `spec/run.sh` to `pass` and move the finding in `docs/verification/README.md` to the fixed list.
- `expected fail on X, got fail ... Y`: the mutant breaks another rule first. Read the trace before you change the expectation.
- `got error`: TLA+ syntax or a type error in the model. Modeling error, not a product bug.
- A node test failing: real-code regression; the model can still pass because it only abstracts the code. A law in `test/laws.test.ts` prints the generated counterexample (the request or log it used); the generators are seeded, so the same case comes back on every run.

## When the change is intended
Update the model action that mirrors the changed code. Keep one model step = one indivisible step in the code: within one Node process each `append` is synchronous; across processes only the lock makes read and write atomic; `prune` lists, deletes and the `verify` and `anchor` commands read without the lock. Keep the mutant cfgs failing. Rerun, then move the sync commit above to the new HEAD only after you have checked that every listed function still matches its model action.
